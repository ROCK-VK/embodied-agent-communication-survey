# 机器狗上行数据的 Wi-Fi CSI 采集与关联

本周调研总结与实验室实操计划｜整理日期：2026-10-10

**当前状态：** 桌面调研与操作方案已整理；尚未确认实验室设备型号，未安装 CSI 驱动、未刷写路由器、未进行真实 CSI 采集。本方案不包含实测日志或原始 CSI 采集文件。

## 一页结论

学长希望研究：机器狗在时刻 t、位置 (x,y) 上传某种视觉或激光雷达相关数据时，记录这条无线传输对应的 Wi-Fi CSI，并把 CSI、传感器数据和机器狗位姿关联起来。

CSI 是接收端对无线信道的测量，工具按符合要求的 Wi-Fi 无线帧生成 CSI 记录。它不会自动知道该帧属于哪条 ROS 消息，也不会直接给出机器狗坐标。要形成可用记录，需要把无线包记录与传感器样本标识、时间戳以及同一时刻的位姿关联起来。

学长给的 Atheros 工具方向有依据，但硬件约束较强。该项目的采集说明要求发送端发出带相应 sounding 设置的 HT 帧，并要求发送端和接收端使用该工具的兼容实现。接收端还必须是能够报告 CSI 的受支持芯片。具体设备要按型号、硬件版本和驱动确认，不能仅凭“有 Wi-Fi”或“是 Orin NX”判断兼容。

**对下周安排的理解：** 如果本周方案与设备条件确认没有问题，下周很可能去实验室做第一轮设备核验和链路实验；目前不是已经确认的时间，也不应理解为下周必须完成机器狗、相机、雷达和定位的全链路集成。首轮应先验证 CSI 链路，再逐步加入业务数据。

## 本周完成的调研成果

以下是截至 10 月 10 日从学长原话、Atheros 项目资料、OpenWrt 文档及最新对话中整理出的桌面调研成果；不代表已经做过实验室操作。

- 明确了测量对象：目标是“上行感知相关数据传输时的无线链路 CSI”，而不是仅测一个位置的 RSSI，也不是默认用 CSI 反推位置。
- 核对了 Atheros 工具的主要限制：目标为 Atheros/Qualcomm Atheros 的 ath9k 802.11n 路线；项目列出的已验证芯片包括 AR9580、AR9590、AR9344、QCA9558。部分 802.11ac SoC 只有在兼容的 802.11n 模式下才适用。
- 核对了该项目标准采集模式的 TX/RX 要求：项目 Wiki 说明 TX 侧要设置 sounding 标志，标准方案要求 TX、RX 两侧安装工具。实际芯片和软件版本仍须现场确认。
- 整理了设备管理与测量链路的区别：电脑到路由器的网线用于管理；TX 与 RX 之间必须通过正在测量的 Wi-Fi 链路传输测试帧。管理网线不能误接成绕过 Wi-Fi 的数据通路。
- 修正了数据粒度的假设：学长没有指定视觉数据一定是原始图片，也没有指定雷达数据一定是原始点云。它们也可能是压缩数据、检测结果或特征；应先核对实际传输内容。
- 澄清了标识字段：sample_id 可帮助识别一条业务样本；chunk_id 只在应用程序主动把样本切成多块时需要。不能因为 TCP、IP 或 Wi-Fi 底层分段，就假设应用层存在同样的 chunk_id。
- 拟定了分阶段路线：设备盘点 → 官方小流量测试 → 带样本标识的受控 UDP → 验证机器狗数据确实经 Wi-Fi TX/RX → 接入真实传感器数据和位姿。

| TX=Client，RX=AP，两者用 Wi-Fi 建立测量链路 | 适合作为首选候选 | 对机器狗向服务器上传的方向，这样安排直观；项目 Wiki 也支持 AP–Client 模式。无线接口名称、管理网段、信道、带宽和加密配置由实际固件决定，不能预设 wlan0 或固定 IP。 |
| 两端都安装 Atheros CSI Tool | 对该项目 Wiki 描述的标准方案成立 | Wiki 说明发送端需要发送相应 sounding 帧，因此要求 TX 与 RX 两端安装工具。TX 与 RX 的芯片能力可以不同；RX 必须能输出 CSI。应按准备使用的确切版本和设备重新核对。 |
| lsmod、/dev/CSI_dev、recvCSI、sendData 可作为检查步骤 | 基本合理，但不能单凭节点存在判成功 | lsmod 和设备节点只说明驱动/字符设备可能已加载。最终验收要看接收记录是否包含有效 CSI（例如 csi_len 大于 0）、时间戳及可解析的矩阵。先用实际固件显示的命令用法；无线接口名不一定是 wlan0。 |
| 发送 100 个测试包就应得到 100 条 CSI | 不能作为精确验收条件 | 工具对符合条件且成功接收的 HT sounding 帧报告 CSI；丢包、帧类型、固件和缓冲会影响数量。验收有效、可解析的 CSI 记录和异常原因，不要求记录数与发送数严格相等。 |
| Jetson 网口接 TX 路由器，RX 网口接电脑 | 可测试的拓扑，不是插线即通 | 还要配置路由、NAT 或其他经批准的转发方式，并确认业务包实际经过 TX→RX 的 Wi-Fi 空口。此方案的无线发射端是外置 CSI TX 路由器，不等同于测 Jetson 自带 Wi-Fi 的 CSI。若目标是 Jetson 原生无线链路，必须另行确认其无线芯片与驱动是否兼容。 |
| sample_id 和 chunk_id 用来把 CSI 对到一帧图片 | 思路可用，但内容假设过早 | sample_id 是推荐的业务样本标识，不是网络强制字段；优先复用已有消息序号。chunk_id 只在应用层主动分块时使用。先确认视觉/雷达数据的实际类型、大小和传输方式；一个业务样本可能对应多条 CSI，但不能直接假设一个应用 chunk 就是一条 Wi-Fi 帧。 |
| Wireshark 用来验证 CSI | 只适合辅助看网络流量 | Wireshark 可以检查 IP/UDP/TCP 流和路由路径，不能替代兼容无线芯片及 CSI 驱动，也不能单靠普通以太网抓包得到 Atheros CSI。 |

核验依据包括 Atheros 项目 Wiki（采集与安装页）、其驱动和用户态源码，以及 OpenWrt 当前通用安装、SSH 和升级说明。Atheros Wiki/指南中包含较早的 OpenWrt 构建步骤；将其视为该项目历史版本的参考，不视为当前任意路由器都可直接套用的刷机指南。

## 候选拓扑与线缆用途

以下只是待学长和实验室设备确认的候选方案。它不代表现有机器狗已经采用这条网络路径。

~~~text
机器狗上的传感器 / 感知结果 / 位姿
                  │
                Jetson
                  │ Ethernet（候选输入链路，需配置转发）
                  ▼
       CSI-TX 路由器（兼容 Atheros）
                  │
                  │  Wi-Fi 空口：实验测量链路
                  ▼
       CSI-RX 路由器（CSI 接收与记录）
                  │ Ethernet
                  ▼
              PC / 服务器

电脑 ── Ethernet ── 当前正在配置的路由器 LAN 口
      （管理链路，可逐台连接；与空口 CSI 测量链路分开）
~~~

| 连接 | 用途 | 注意 |
|---|---|---|
| 笔记本 RJ45 → TX 或 RX 的 LAN 口 | 首次登录、核对配置、必要时管理设备 | 可逐台换线；不要先接 WAN。电脑没有 RJ45 时才考虑 USB 转 RJ45。 |
| CSI-TX 无线接口 ↔ CSI-RX 无线接口 | 产生被测 Wi-Fi 传输和 CSI | 首轮测试中，两个设备间不要另接会绕过空口的网线或交换机。 |
| Jetson 网口 → TX 路由器 LAN | 候选的业务数据输入 | 只有路由配置完成后数据才会到 RX；若要测 Jetson 原生 Wi-Fi，这种接法不等价。 |
| RX 路由器 LAN → PC/服务器 | 访问接收数据、管理网络 | 需确认 IP/路由无冲突；首轮官方测试可以先用电脑逐台管理，不必一次接全。 |

## 本周末与进实验室前的准备

1. **确认设备清单。** 请实验室给出或现场记录 TX、RX 的品牌、完整型号、硬件版本、Wi-Fi 芯片、当前系统/固件及是否已有 CSI 固件。记录机器狗/Orin NX 当前用的无线设备、数据发送方向和接收端。不要把 Orin NX 模块名称当成无线芯片型号。
2. **确认测量目标。** 和学长核对“视觉/激光雷达数据”是原始传感器流、压缩流、特征，还是处理后的感知结果；以及先要实际业务无线帧的 CSI，还是接受同一时刻附近的探测包 CSI。二者的证据含义不同。
3. **确认坐标来源。** 问清 (x,y) 来自机器狗的 odom/SLAM/TF 还是实验室外部定位；检查其时间戳如何和传感器消息对应。CSI 自身的硬件时间戳不应直接当作 ROS 时间。
4. **本机只作管理和分析准备。** Windows 自带 OpenSSH 客户端的机器通常可直接用 PowerShell；进实验室前可运行 ssh -V 检查。Wireshark 或 WinSCP 是可选工具。之后如需解析 CSI，可用单独 Python 虚拟环境。当前不需要改 WSL 内核、装 ath9k 驱动、改 Docker、编译或刷写 OpenWrt。
5. **预先确认权限和恢复方法。** 如果两台设备未装 CSI 固件，先确认设备属于谁、是否允许刷写、如何备份及恢复。没有硬件型号和对应镜像时，计划停在盘点，不试刷。

> 学长好，我按“CSI 接收端记录逐个 Wi-Fi 帧的信道状态，再把它与感知数据样本和机器狗位姿关联”整理了方案。Atheros 项目的标准采集流程要求 TX/RX 使用兼容的工具实现。实验室现有 TX、RX 设备具体是什么型号和硬件版本，是否已经刷好 CSI 固件？机器狗数据现在走自身 Wi-Fi，还是计划经外置 CSI 路由器转发？另外，您说的视觉/雷达数据是原始传感器数据还是处理后的感知结果？

## 实验室首轮实操卡

### 0. 到场先盘点，不先刷机

记录设备标签、完整型号和硬件版本；拍下接线前状态；询问是否允许修改固件。分别记录 TX/RX 的现有管理地址、OpenWrt 版本、无线芯片和接口。先区分设备是否已装实验室验证过的 CSI 固件。

**停止条件：** 型号/revision 不清楚、镜像不匹配、设备正在服务其他项目、没有备份/恢复方案或未获刷写许可时，不刷机；先将问题带回和学长讨论。

### 1. 用网线管理设备

一次管理一台设备：电脑网口接该路由器 LAN；按设备现有地址或 OpenWrt 默认地址进入 LuCI。设置/确认 root 密码后，可从 Windows PowerShell 登录：

~~~powershell
ipconfig
ping <设备管理地址>
ssh root@<设备管理地址>
~~~

`ipconfig`、`ping` 和 `ssh` 在 Windows 电脑运行。登录成功后出现 OpenWrt shell 提示符，以下检查命令才在路由器上运行：

~~~sh
ubus call system board
uname -a
iw dev
lsmod | grep ar9003_csi
ls -l /dev/CSI_dev
command -v recvCSI
command -v sendData
~~~

无线接口名可能不是 wlan0；用 iw dev 的实际输出。若 CSI 模块或命令不存在，先记录现状并确认固件方案，不继续假装已经具备采集条件。

### 2. 确认两端 CSI 能力并建立隔离无线链路

只有 TX 和 RX 的芯片/固件都核对后才进入此步。候选配置是机器狗侧 TX 作为 client/STA，服务器侧 RX 作为 AP；固定信道和带宽以硬件支持、实验室环境及所在地法规为准，不直接照抄教程里的信道 6。给两台路由器分配不冲突的管理地址，避免默认地址相同造成冲突。

TX 的 iw dev <接口> link 应显示已连接到目标 AP。确认接收端记录 CSI 的无线接口就是这条 Wi-Fi 链路。电脑的管理网线留在 LAN 管理侧，不要把 TX LAN 和 RX LAN 用交换机直连成可能绕过无线的数据通路。

### 3. 官方最小测试：先不接机器狗

先在 RX 上启动接收：

~~~sh
recvCSI /tmp/csi-test.dat
~~~

再在 TX 上确认 sendData 的实际命令用法，使用真实无线接口和 RX 的无线 MAC 发一小批测试包。项目 Wiki 示例形式如下，参数应按设备中实际程序的帮助/用法核对：

~~~sh
sendData <TX无线接口> <RX无线MAC> <测试包数>
~~~

测试后检查文件是否非空，并用项目配套解析工具检查记录。至少确认有有效 CSI 长度、可解析的复数 CSI、接收时间戳和 RSSI 等元数据。模块加载、设备节点存在、文件非空都只是局部检查；不能替代有效 CSI 内容。

**通过条件：** 在 TX→RX 的 Wi-Fi 测试链路上得到可解析、CSI 长度非零的记录。实际记录数量可以少于发送数量；差异要按丢包、帧类型、驱动或采集缓冲调查。

### 4. 验证业务标识与 CSI 能否对应

最小官方测试通过后，再发可控的小 UDP 消息，例如带固定标记、sample_id、sensor_type 和发送时间。先确认接收端 CSI 记录所保存的 payload 能否读出这些字段，并确认该记录确实来自本次 TX→RX 空口传输。

若后续数据本身有 ROS 消息序号或稳定 ID，优先复用。只有应用程序主动切分一条业务数据时，才增加 chunk_id/chunk_count。一个 sample 可能对应零条、一条或多条有效 CSI 记录，需在实验中统计，不能预设严格一对一。

### 5. 再验证 Jetson 转发路径

若学长同意采用外置 CSI TX 路由器，先让 Jetson 发送很小的 UDP 测试消息到 PC/服务器。通过受控接线和路由配置确认数据必须走 TX 无线接口到 RX，RX 再经以太网交给服务器。同步检查路由/接口计数与 CSI 接收记录；先不接相机和雷达。

**通过条件：** Jetson 发出的可识别测试数据确实到达服务器；接收 CSI 记录与该测试流能建立可复核的对应。若路由流量不出 CSI，先查 TX 的 sounding/转发路径和 RX 兼容性，不直接上 ROS 大流量。

### 6. 加入位姿和真实感知数据

先确认实际话题/数据类型和大小，再选一个低风险数据流。用传感器消息自身时间戳和序号记录样本；从 odom/TF/SLAM 或认可的外部定位来源取同一时间附近的 (x,y)。记录 CSI 硬件时间、CSI 元数据、接收序号和数据关联依据。必要时做时钟偏差校正，但不要把 CSI 硬件 TSF 与 ROS 时间戳直接相减当作同步误差。

相机和雷达分开逐一接入，确认匹配率、漏记情况和时间差后再并发。移动/不同位置测试放在静止链路、标识关联和位姿记录都通过之后。
