# 多模态关联离线优化

本轮只使用本机代码与已有实验数据，不连接设备、不启动采集或控制。所有位置与传感器时间的设备端表现仍需现场核实。

## 真实数据的离线索引

`multimodal_offline_index.py` 汇集发送端、接收端、保存的原始样本、此前验证的 CSI 内解密结果、PCAP 字节比对和原始 CSI 记录。索引按 sample→chunk→packet→CSI record 记录一对多关系，保留原始时间戳和缺失；同时核对样本 SHA-256、传输字段、CSI 结构标记及既有 PCAP 唯一匹配。它**复用此前解密和分片字节验证的结果，并不重新解密或独立证明位置关系**。

真实数据复核 212 个发送 ID、212 个接收 ID、138 个已匹配 ID 和 138 条 CSI 记录。采集元数据仍标明位置不可用。索引输出为私有文件；当前 v3 是本轮有效结果。最初试运行的无版本索引因程序字典副作用误报 212 个匹配 ID，已修复并用缺失包测试覆盖，旧文件保留但不能使用。

程序可通过参数指定未来的 sender、receiver、匹配结果和 CSI 路径，但仍要求复用当前 JSON/JSONL 契约及 RxSBasic v4；不能自动读取任意格式。未来元数据可包含 `position_samples`（每条有 `position_sample_id`、位置、原始采样时间和时钟域）和 `position_associations`（含 `sample_id`、`position_sample_id`、`association_basis` 和 `association_evidence`）。程序只检查输入关系存在、依据非空并原样保留，**不独立验证该依据有效、不自动做时间近邻关联**。采集端还需真正生成经核验的这些记录。

## Go2 位置和时钟

现有状态桥启动并发送外层消息，不代表收到 DDS 状态。历史采集只订阅 `rt/sportmodestate`；当时约 8 秒未成功保存位置信息，且未分开统计消息回调和解析异常。宇树 ROS2 文档同时列出运动状态的高频与低频主题，官方 Go2-W SDK 示例使用 `rt/lf/sportmodestate`；本机 Go2 是否提供低频主题未验证。还应考虑实际 DDS 接口、域、发现、QoS、消息类型和机器人状态发布模块，不能把某一项当成已确认根因。[宇树 ROS2 文档](https://github.com/unitreerobotics/unitree_ros2)；[官方 Go2-W 示例](https://github.com/unitreerobotics/unitree_sdk2/blob/main/example/go2w/go2w_sport_client.cpp)。

`go2_state_readonly_probe.py` 为后续现场准备：只订阅 `rt/lowstate`、`rt/sportmodestate`、`rt/lf/sportmodestate`，分别记初始化错误、回调次数、解析错误，以及原始 stamp、Jetson 接收 wall/monotonic 和 boot ID。它不发送运动控制指令，尚未在真实设备部署或执行；模拟回调测试不等同 DDS 联通验证。官方状态示例将 position 描述为 odometry frame，本机原点、方向、单位、复位语义和时钟域仍需核实。[官方状态读取示例](https://github.com/unitreerobotics/unitree_ros2/blob/master/example/src/src/read_motion_state.cpp)

历史上某个服务启动时的系统 wall time 显示 1970，后来系统显示 2026 和 NTP synchronized；只能确认显示异常，不能确定 RTC、启动前同步、时钟跳变或日志显示是原因。未来需要同时保留 boot ID、wall 和 monotonic 的多次成对采样及同步状态，再检查启动前后的 journal 实时和 monotonic 时间。monotonic 仅在同一设备同一次启动内比较；NTP 状态为 synchronized 不等于测得跨设备偏差。[systemd journal 时间说明](https://www.freedesktop.org/software/systemd/man/254/sd_journal_get_monotonic_usec.html)

## 传感器时间与传输

- MID360 本次 5 个包的 `time_type=0`，按 [MID360 官方协议](https://github.com/Livox-SDK/livox_wiki_en/blob/master/source/tutorials/new_product/mid360/livox_eth_protocol_mid360.md)表示无外部同步源、以雷达上电为起点的纳秒。原始 8 字节按本次格式小端解释约为上电后 5519.722644–5519.724564 秒，相邻包原始时间差均为 0.48 ms；Jetson 用户态接收间隔不同。需现场确认型号、协议/固件版本，不能把它当 UTC 或直接与 Jetson 时钟相减。
- D435i 应在同一次实际 frameset 获取 RGB 与 Depth，并分别保存设备提供的 frame number、timestamp、timestamp domain 和采集端接收时间；仅从两个独立“最新缓存”请求无法证明配对。帧时间值只有在已知共同时间域或经过标定映射时才可比较。[RealSense 帧接口](https://github.com/realsenseai/librealsense/blob/master/include/librealsense2/h/rs_frame.h)
- `multimodal_udp.py` 工作区增加单样本 64 MiB 上限、同一 packet_id 内容冲突时拒绝；CRC、边界与冲突均经过本地合成测试。单样本上限不限制多样本累计内存，也不提供认证、可靠重传或拥塞控制；上线前需实机测试。设备端运行版本未更新。
- 旧相机服务不暴露原生时间和配对 ID；替换或扩展服务需要现场核验现有管线与兼容性，不能仅凭现在缓存 JPEG 倒推出曝光时刻。

## 已匹配 CSI 的时间间隔

分析使用本次真实多模态实验中 138 条已匹配 CSI 的接收端 `RxSBasic` v4 `SystemTime`；[PicoScenes 官方文档](https://ps.zpj.io/manual/matlab.html)将其描述为接收主机驱动记录的 epoch 纳秒。这里不把它与 Jetson 或传感器时钟直接相减，记录顺序未观察到倒退。

| 指标 | 本次结果 |
|---|---:|
| 首末已匹配 CSI 的跨度 | 14.112 秒 |
| 相邻间隔中位数 / P95 / 最大 | 67.25 / 215.27 / 605.34 毫秒 |
| 超过 500 毫秒的相邻间隔 | 2 次 |
| 100 毫秒完整窗口为空 | 35 / 141 |
| 500 毫秒、1 秒完整窗口为空 | 0 / 28、0 / 14 |

窗口为从第一条匹配开始划分的固定非重叠窗口，只统计首末匹配之间的完整窗口。改变窗口起点可能改变结果；“固定 500 毫秒窗口无空窗”与“最大间隔超过 500 毫秒”可以同时成立，不能解释为任意 500 毫秒都有 CSI。首条之前、末条之后、其他未匹配业务及背景 CSI 不包含在上述指标中。

本次存在 600 毫秒级空隙，因此不能声称可靠的 10 Hz 全覆盖。采样密度应由应用对时间误差和空间误差的要求倒推：例如允许移动距离误差为 `d`、最大速度为 `v` 时，关联时间的不确定性须控制在约 `d/v` 之内；还要计入位置误差、传感器与 Jetson 及接收端时钟误差、缓存和传输延迟。仅提高发包频率不能保证 CSI 捕获、有效关联或同步。先定义任务容许误差，再用重复的长时间测试检查 P95/P99 间隔、最大缺口和空窗。

## 使用与下次现场优先级

本地生成索引：`python multimodal_offline_index.py --capture <本地结果目录> --output <新的私有JSON>`；未来目录通过 `--source --receiver --derived --csi` 分别指定。输出会包含图像/雷达与设备时间元数据，必须按私有材料保存。验证运行：`python -m unittest -v test_multimodal_offline_index test_multimodal_udp_offline test_go2_probe_offline`。

下次优先在机器狗静止时运行三主题只读诊断，确认位置、状态发布与 stamp；同时记录设备型号/固件和两个主机多次 wall/monotonic 锚点。然后在现有相机管线内取得成对 frameset 和原生时间，读取 MID360 上电时钟与同步状态，建立带已验证时钟映射或明确误差界的近实时数据链。真实机器狗运动与更长的稳定性测试必须待这些基础数据可用后开展。
