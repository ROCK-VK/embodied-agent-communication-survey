# 实验2联网核验与实现边界

核验：2026-10-14。独立项目sniffer_jetson，ESP-IDF5.5.5；不是Router例程，不修改已通过基线。

## 联网核验

- git ls-remote确认[esp-csi](https://github.com/espressif/esp-csi) master为8633d67152db2808f141cc1595970aa9cf406045；下载并核验router/RX当前源码。Router回调只接受AP BSSID，不能原样作为第三方STA监听判断程序。
- [C5 IDF5.5.5 Wi-Fi Guide](https://docs.espressif.com/projects/esp-idf/en/v5.5.5/esp32c5/api-guides/wifi.html)明确NULL/STA/AP/APSTA均可启用sniffer，帧类别/过滤及回调任务边界有文档；抓到帧不代表该帧有CSI。
- [该版C5头文件](https://github.com/espressif/esp-idf/blob/v5.5.5/components/esp_wifi/include/esp_wifi_he_types.h)区分legacy/HT20/HT40/VHT20/HE20采集，VHT选项不是80MHz支持；rx格式1为11g/11a别名、2 HT、3 VHT、4 HE SU。保留原始PHY字段，不能仅凭“AP是80MHz”标每包80MHz。
- [#124](https://github.com/espressif/esp-csi/issues/124)：S3 sniffer问题，协作者说明来自其他TX的CSI描述TX→本接收端；不能推为C5任意模式保证。
- [#229](https://github.com/espressif/esp-csi/issues/229)：C6商用下行数据帧失败，贡献者提示PHY/MCS/聚合/带宽/beamforming/主信道等要核对；后续用户限制20MHz仍失败并提供空口数据。不是C5已证伪，也不是单靠20MHz就保证成功。
- [#265](https://github.com/espressif/esp-csi/issues/265)：C5 sniffer经同Wi-Fi UDP导出出现Windows问题的社区报告；本实现只UART，未关闭Windows防火墙/安全软件或改网络。
- [#270](https://github.com/espressif/esp-csi/issues/270)：社区C5高速改固件案例，不照搬1000Hz保证。
- [esp-idf#18493](https://github.com/espressif/esp-idf/issues/18493)：C5 5GHz CSI buffer静态数据问题报告；因此除metadata有效字段，还保留buffer/长度/不同buffer数，不用“callback触发”代替数据质量。

## 实现与统计

- NULL模式，无connect/scan/AP/DHCP客户端/业务流量；不读取旧SSID密码来关联网络。用户仅通过UART发送CFG（信道和目标MAC），没有Wi-Fi CSI回传。
- promiscuous和CSI独立计数。以802.11 header Address2/TA判目标TX，ACK/CTS没有TA，RA匹配不算TX；MIMO/misc无header不解引用。mgmt/data/ctrl的解析条件不同，保留FC/seq/direction，禁止把AP转发当Jetson上行。
- CSI保留API source、header TA、FC/seq、timestamp、RSSI/channel、PHY原始字段、len与未增益补偿SDK buffer；valid=1/rx_state=0及非空/长度匹配为最低有效性门禁，first_word_invalid单列，来源冲突另计。
- 所有callback统计保留；目标详细记录全部尝试入队，非目标FRAME/CSI每64条抽样用于诊断。队列深度32、CSI最多复制2048字节；溢出/截断明确统计，不能静默当无线丢包。
- callback不printf、不阻塞I/O；独立输出task经UART921600导出。STOP先关闭ESP CSI/prom，再排空队列、FINAL，主机关闭COM。
- 同一无线帧证据仅比较RX timestamp/TA/FC/seq，不做UDP/sample_id关联。最终A/B/C/D是观测类别，负结果须先审计目标在场/在线，不能自动推导能力。

## 初始化失败与版本一致性

- v1的NULL模式STA带宽API返回InvalidArg，尚未ARMED，不能分类为监听失败。已删除该调用，实际接收带宽不直接确认，rx_bw=null；只固定/读取主信道。
- v2的secondary query变量未初始化出现非法输出，不能作为副信道/带宽证据；v3初始化该值，并增加所有帧类别/可解析TA/背景FRAME样本，防止只有目标过滤结果而无法审计解析器。
- 现有ack_csi=false代表配置意图；v2实际仍见ACK类背景CSI，不能声称驱动完全阻止ACK回调。ACK无TA且source不确认，不作为Jetson发射证据。
- 已通过v3纯build与分区大小检查；具体烧录/运行版本由各run的manifest/ELF hash确认，不因源码已更新就默认设备同步。
- 历史失败与采集原文只本地保存；GitHub仅源码、核验说明、匿名结果与hash。现场缺独立20MHz AP/普通STA，不用现有小米/Jetson切网替代对照。

## 2026-10-15自定义UDP packet_id准备

- ESP-IDF 5.5.5本机原生头文件`components/esp_wifi/include/local/esp_wifi_types_native.h`的`wifi_csi_info_t`包含`hdr`、`payload`和`payload_len`。这证明回调结构提供相关指针/长度字段，但不保证旁路未关联设备能解密受保护的802.11数据帧。
- 新版sniffer只在Frame Control的Protected位为0时，尝试从LLC/SNAP→IPv4→UDP载荷读取固定`CSID`探针；受保护帧明确计数并跳过，不导出802.11/业务原始payload。FRAME与CSI分别记录packet_id；分析器用timestamp、TA、FC、seq_ctrl单独统计所有目标FRAME↔CSI匹配和有ID的FRAME↔CSI匹配。
- 检测器校验协议版本、长度、保留位、固定测试数据和CRC32。它只覆盖本项目的无分片IPv4/UDP测试帧；不解析IPv6、IP分片、加密payload或任意业务协议。
- packet_id协议/收发/捕获/分析工具见`数据传输与CSI关联方案.md`及同目录`udp_probe_*.py`、`capture_packet_id.py`、`analyze_packet_id.py`。C5 v5 app已烧录并经READY/采集确认；源码/build/实机版本一致。
- 最终60.204秒实机轮次：Jetson sender发送100包，Windows receiver收到并校验100/100；缺失/重复/无效均0。C5记录63条目标Data FRAME及63条有效目标Data CSI，drop=0，Protected=1为63/63；timestamp/TA/FC/seq_ctrl元数据一对一配对63/63，但FRAME与CSI侧均无法读出packet_id，端到端业务ID↔CSI未建立。未改变Jetson网络/防火墙策略；接收器使用Windows Public profile下已有的Python UDP入站允许规则。
- 接收器早期几轮因空闲超时/启动顺序未与sender重叠；另一次使用的Python执行路径与已有允许规则不一致。最终扩大接收器空闲超时并使用已允许解释器后成功；不把早期0接收误解成网络阻断。第一次串口sanity漏掉RTS复位而错过READY；捕获器现已复用已验证采集器的RTS复位流程。错误idf.py调用转入build_ascii并在写设备前中止，后改用精确app镜像直接烧录。首次默认`export.ps1`因系统python选择不存在的3.13环境失败；构建使用专用Python3.11显式调用`tools/activate.py --export`。
- 离线验证仍通过：5个Python脚本语法、20包loopback（20/20、缺失/重复/无效0）以及合成FRAME→CSI匹配。原始sender/receiver/UART/CSI数据只保存在本地结果目录。
