# HT主方案与WPA2业务关联计划（2026-10-16）

## 本轮结论

1. **实机软件+枚举对照确认：当前2.4GHz HT20主方案。** SSH读取2417MHz/channel2，rf_info `cur_bw=0 / oper_bw=0 / offset=0`，ap_info `cur_bwmode=0 / bwmode=0 / ht_en=1 / vht_en=0 / sgi_20m=1 / sgi_40m=0`。候选同版本RTL8821CU源码`include/cmn_info/rtw_sta_info.h:69`定义CHANNEL_WIDTH_20=0、40=1；不由CSI len114或rx_format2推断带宽。源码候选非模块逐字节溯源，结论是当前驱动状态HT20，不是逐PPDU波形测量。
2. **实机当前协商：WPA2-PSK、pairwise CCMP、group TKIP、wpa_state COMPLETED。** 普通wpa_cli权限不足后，仅sudo只读status成功；未读取PSK/密钥。AP缓存广告WPA1/WPA2、PSK、pairwise TKIP/CCMP、group TKIP，是兼容模式；当前不是WPA3/SAE，不能把AP的TKIP能力当本次单播TKIP。
3. **明确结论B：昨天/今天旧记录不足离线解密，需要另一次完整raw Data+EAPOL采集。** 现有v5/v6c实际导出FRAME元数据+CSI raw bytes；`data_hex/hx`是信道估计字节，不是802.11 payload。没有完整MAC header/密文/CCMP header/IV-PN/MIC/FCS/EAPOL，不能补造标准真实802.11 pcap，更不能从这些数据还原密文。
4. sniffer-7已建立独立目录、构建及离线验证通过，**没有烧录、没有新硬件采集、没有重关联、没有发UDP**。板上最后验证版本仍v6c、STOP状态；候选与实际运行明确分开。
5. VHT20、5GHz、tx_bw_mode、ESP AP、Pi/AX210后置；当前先解决HT20条件下Protected业务ID关联。Jetson/AP/网络/驱动/ROS/服务/eth0/机器狗均未修改。

## 旧数据完整性审计

| 字段/内容 | 现有实际保存 | 作用/缺口 |
|---|---|---|
| FC、seq_ctrl、TA、RA、时间戳、PHY/RSSI | 有 | 可作FRAME↔CSI元数据匹配 |
| 完整MAC header | 无 | Duration、Address3/4、QoS/HT control原字节缺失，不能根据TA/RA反造 |
| Protected、Retry等FC位 | 可由保存FC解码 | 不是完整header替代物 |
| 原始Protected payload | 无 | 没有CCMP header/PN/密文/MIC，无法解密 |
| FCS | 无 | FCS本身不是WPA2解密必要条件；关键缺口是密文+握手 |
| 原始EAPOL/4-way | 无 | 未安排关联期捕获，旧过滤只导出目标Data元数据 |
| sender/receiver探针日志 | 有 | 证明端到端100/100；不能据此指定某条加密帧含哪个ID |
| CSI114/106字节 | 有 | 不能替代帧体，也不能用于反推业务payload |

`existing_data_audit.json`列出实际各目录事件数/字段名，未扫描或导出Wi-Fi密钥。可将旧元数据封装为自定义统计文件，但不能冒充可解密的真实抓包。

## sniffer-7 binary设计

独立源码`ESP32测试/sniffer_7_raw/`，不覆盖`sniffer_jetson`的现行v6c。ESP仍WIFI_MODE_NULL，无AP关联、扫描、发包或网络回传。

- CFG必须输入本次确认的信道、Jetson MAC、AP BSSID；不包含SSID/密码。
- promiscuous只导出**精确Jetson/AP对的双向Data MPDU**，这样保留上行受保护Data和AP→Jetson EAPOL；不采其他客户端，Mgmt/Control不逐条输出。Protected的EAPOL不能靠明文标记识别，但因pair双向Data保留策略不会被丢掉。
- 可识别的未保护LLC/EAPOL仅加标签；不把EAPOL存在等同捕齐4-way。不在C5执行WPA密码学。
- CSI只保留source/TA=Jetson、RA=目标AP、有效Data CSI；原始CSI字节、valid、rx_state、first_word_invalid、rx_seq保存。
- 固定24槽池/指针队列、16KB UART TX ring、921600 baud；raw cap4096、CSI cap2048。超cap明确TRUNCATED并计数，保留orig/copy长度；不得当完整包解密。内存/新吞吐尚未实机验证。
- 接收回调仅过滤/拷贝/入队；CRC/封装/输出在独立task。STOP关闭CSI/sniffer后排空，FINAL有计数及heap，UART drain后退出任务。

### CS7R v1 wire格式

头部62B、payload N字节、CRC32 IEEE小端4B；CRC覆盖头+payload，所有多字节字段显式LE，不直接导出编译器bitfield/struct布局。

| offset | 字段 |
|---:|---|
|0..7|magic CS7R、version1、kind（RAW1/CSI2/STATS3/ARMED4/FINAL5）、header_len62|
|8..23|record_serial u32、ESP rx timestamp u32、ESP monotonic callback us u64|
|24..31|FC u16、seq_ctrl u16、channel u8、PHY u8、RSSI i8、rx_state u8|
|32..39|flags u16、original_len u16、copied_len u16、SDK sig_len u16|
|40..61|TA6、RA6、CSI source6、rx_seq u16、valid u8、first_word_invalid u8|

flags：FCS_ABSENT1、TRUNCATED2、EAPOL4、UPLINK8；RAW payload为SDK dump_len原始MPDU字节；CSI payload为原始CSI；控制记录为紧凑JSON计数。

Windows从RAW按FC实际长度解析Duration、Address1/2/3/4、QoS、HT control、Protected/Retry/MoreFragments/ToDS/FromDS、fragment/seq。24B基础头+可选Addr4 6B+QoS 2B+可选HT control4B；不固定偏移乱切。A-MSDU、fragmented、protected不进入简单明文UDP解析，交成熟工具处理。

官方IDF5.5.5 C5 `dump_len`明确排除FCS，因此复制dump_len、不按sig_len越界读取；pcap标记无FCS。**真实SDK是否完整保留CCMP IV/PN/MIC、聚合MPDU呈现方式，必须下一轮用raw实测核对，不能因代码拷贝就宣称已经确认。**

### UART预算与重新验收

921600/8N1理论约92160B/s；一RAW开销66B，一114B CSI共180B。一对的预算约`Lraw+246`B：例如126B小包MPDU约372B，1500B MPDU约1746B。理论上限不含统计、调度/USB余量；实际应保留至少20%余量，并用wire_bytes/host bytes验证。

完整raw消除了hex的2倍膨胀，但AP下行、背景流量、聚合/突发仍可能使队列满。24槽仅缓冲突发，不能增加持续带宽；不能沿用v6c零drop结论。raw cap4096不覆盖所有可能的大A-MSDU，出现截断即本轮完整抓包门禁失败，不悄悄删后宣称成功。

下一轮先30秒raw被动sanity：CRC/序号/长度/parse/queue drop/truncation/write error为0，callback→enqueued→output→host闭合，FINAL成功、有HT有效CSI及匹配、检查heap。若失败，先停，不重关联/发probe。完整EAPOL和所有Wi-Fi帧的100%覆盖不作为空口保证。

## Windows离线工具链

- 官方Wireshark Portable4.6.9只提取本地文件，SHA256与官方公告匹配；没有装Npcap、服务、抓包驱动或改系统PATH。推荐现有ASCII junction `D:/CSI_Wireshark/tshark.exe`；原中文路径曾引发可选Falco插件加载警告，ASCII入口已确认stderr0。
- `capture_raw7.py`（本轮未运行）保存stream.bin及逐serial主机wall/mono时间侧录；收到READY才CFG，校验ARMED pair/channel，超时STOP/FINAL，未取得FINAL不得进入下一步。
- `convert_raw7.py`离线校验CRC、长度边界、序号连续；失败不生成pcap。生成normalized records、joins、radiotap PCAP、frame_index侧录。PCAP linktype127，radiotap仅flags/channel/RSSI，不伪造HT MCS/TSFT；时间来自主机接收wall time，ESP时间仍留在metadata，不冒充同步时钟。
- pcap→Wireshark专用私有profile→输入合法WPA测试网络SSID+密码→开启IEEE802.11 decryption。**不把现场密码/PSK写到命令行、仓库、报告或JSON**；使用GUI profile/UAT私有配置，完成后不公开profile。
- `extract_tshark_ids.py --profile <私有profile>`仅调用tshark、提取UDP payload并使用既有CSID协议验证run_id/packet_id/sender_mono_ns/CRC；不实现PTK/CCMP/MIC算法。
- `associate_ids.py`经pcap frame_number→record_serial→timestamp+TA+FC+seq_ctrl→CSI列表。保留多个frame/多个CSI、重传、frag、PHY、RSSI、端点时间；不按1:1强配。tshark重组后显示UDP的frame不自动代表所有分片/A-MSDU组件，完整祖先映射尚未实现/验证，结果明确标partial；第一轮小包仍须检查实际是否出现这些情况。

## 下一次现场需要用户做什么（本轮停止，不执行）

1. 用户再次确认后才能烧录sniffer7并执行30秒raw sanity；现场先保持Jetson/AP网络不变，不操作狗/传感器。
2. sanity通过后ESP先进入监听；用户再次授权**我们自己的Jetson重新关联同一当前WLAN**，才触发该会话4-way握手。重新关联会中断当前wlan0 SSH，必须现场显示器/键盘或已验证独立管理通道，不能通过当前SSH盲断网；不改SSID、不改AP、不deauth其他客户端。
3. 已存Wi-Fi profile可能使Jetson无需重输密码；Windows解密profile仍需要用户本地输入合法SSID+密码。Agent本轮不读取/导出其PSK、不需要用户现在在聊天重新发密码。
4. 确认握手记录与目标pair、EAPOL message/replay/方向/nonce是否齐备，再100个48B/5pps probe约20秒、总采集约60秒，STOP/FINAL后离线tshark解密/关联。
5. 原始protected帧/握手/配置仅本地；公开统计先匿名。捕齐EAPOL消息不等于解密必然成功，最终须tshark解析出CRC有效probe并关联CSI为证。

采集本身预计约2–3分钟（30秒sanity+重关联/60秒窗口）；连同首次烧录、现场检查及离线分析预留15–30分钟。握手漏失或raw导出饱和则先停修正，不自动反复重连。这个时间只是计划估计。
