# 0. 当前目标

项目最终目标：

```text
t 时刻
(x,y) 位置
机器狗发送视觉 / LiDAR 数据
        ↓
实际业务 packet / chunk
        ↓
802.11 Data frame
        ↓
对应 CSI
```

当前已经不是“ESP 能不能采 CSI”的探索阶段，而是继续解决：

1. **PHY 覆盖**：原5GHz实机只证明部分legacy；2026-10-16信道2新增HT Data/CSI实证（sanity导出受限）；尚未实测VHT20，更无法覆盖 VHT80。
2. **业务关联**：当前 Data frame 全部 `Protected=1`，旁路 C5 看不到 UDP payload，因此 `packet_id ↔ CSI` 尚未打通。
3. **完整性**：100 个 UDP 包不能直接和 63 个 802.11 Data frame 做数量比，尚不能声称 C5 捕获了全部 Data frame。

## 1.3 CSI 物理合理性验证

已做：

- Static
- Hand-Blocked
- Recovery
- Hand-Motion
- Recovery
- 5 cm 补充遮挡

结果：

- Run A 因用户不小心碰到线导致 ESP 移动，作为无效静止基线保留但不参与正式比较

结论：

> CSI 对动态环境变化具有物理响应的证据已经建立；静态遮挡重复性尚未完成严格验收。

## 1.4 UDP `packet_id` 探针实机测试

拓扑：

```text
Jetson
  │
  │ UDP 探针
  ▼
小米路由器 / WLAN
  │
  ├────────→ Windows UDP receiver
  │
  └────────→ ESP32-C5 旁路 sniffer
```

探针：

- 48 Byte / 包
- 默认 5 包/s
- 共 100 包
- 含：
  - `run_id`
  - `packet_id`
  - Jetson monotonic timestamp
  - 固定测试字节
  - CRC32

实测：

| 项目 | 结果 |
|---|---:|
| Jetson sender | 100 |
| Windows receiver | 100 / 100 |
| 缺失 | 0 |
| 重复 | 0 |
| 格式错误 | 0 |
| C5 采集窗口 | 60.204 s |
| 目标 Data FRAME | 63 |
| 有效目标 Data CSI | 63 |
| FRAME queue drop | 0 |
| CSI queue drop | 0 |
| FRAME ↔ CSI 元数据匹配 | 63 / 63 |
| Protected | 63 / 63 = 1 |
| ESP 可见 `packet_id` | 0 |
| `packet_id ↔ CSI` | 未建立 |

已经打通：

```text
UDP业务发送             ✅
Windows业务接收         ✅
Jetson Data frame捕获   ✅
Data FRAME ↔ CSI       ✅
```

尚未打通：

```text
packet_id ↔ Data FRAME ↔ CSI   ❌
```

原因：

```text
802.11 Data frame
        ↓
Protected = 1
        ↓
旁路 ESP 看不到 UDP payload
        ↓
无法读取 packet_id
```

重要边界：

> `100 个 UDP packet ≠ 100 个 802.11 Data frame`

因此：

```text
63 / 100 = 63%
```

不能解释为 Data frame 捕获率。

# 2. 当前核心问题

## 2.1 PHY 覆盖问题

Jetson 当前网卡：

```text
RTL8821CU
```

之前实机状态：

```text
5 GHz
channel 149
802.11ac / VHT
当前链路高可信为 80 MHz
```

小米 R4 本身支持：

```text
VHT20
VHT40
VHT80
```

因此 AP 能力不是问题。

ESP32-C5：

```text
legacy OFDM    ✅
HT20 / HT40   ✅
VHT20         ✅
VHT80         ❌
```

当前旁路实验证明：

```text
Jetson某些legacy上行Data
        ↓
C5能解调
        ↓
可产生CSI
```

但对于：

```text
Jetson VHT80 Data
```

C5 没有 VHT80 PHY 能力，因此可能直接无法接收。

这是目前旁路 C5 路线的核心硬件限制。

---

## 2.2 Protected payload 问题

C5 当前可见：

- TA / RA
- Frame Control
- `seq_ctrl`
- 接收 timestamp
- PHY metadata
- CSI
- `Protected` 标志

但 Data payload 受 WPA/WPA2 保护后：

```text
UDP
├── run_id
├── packet_id
└── payload
```

旁路 ESP 无法直接读取。

因此：

```text
FRAME ↔ CSI
```

已成立，

但：

```text
packet_id ↔ FRAME ↔ CSI
```

尚未成立。

---

## 2.3 完整 Data frame 捕获率未知

目前不能回答：

> “C5 到底看到了 Jetson 全部 Data frame 的多少？”

原因：

- 没有独立空口 ground truth
- UDP packet 数不是 Wi-Fi frame 数
- 存在：
  - 聚合
  - 重传
  - 分片
  - 后台流量
  - 不同 PHY
  - VHT80 帧可能对 C5不可见

未来需要第二参考监听节点做对照。

# 4. P1：优先只修改 Jetson，限制上行 TX 到 20 MHz

## 4.1 为什么先改 Jetson，不先改 R4

小米 R4 已经支持：

```text
VHT20 / VHT40 / VHT80
```

因此：

> 不需要为了“让 AP 支持 VHT20”去改路由器。

本项目当前主要关心：

```text
Jetson → ESP
```

这一方向的上行 CSI。

只要 Jetson 实际上行 Data PPDU 被限制到 20 MHz：

```text
AP BSS 仍然可能是 VHT80
Jetson 上行实际 TX 可以是 20 MHz
```

对于 C5 验证已经有价值。

因此：

> 第一选择 = 只控制 Jetson TX bandwidth。

---

## 4.2 首先只读核查 RTL8821CU 驱动能力

第一步不要改任何东西。

确认精确驱动模块名：

```bash
readlink -f /sys/class/net/wlan0/device/driver
ethtool -i wlan0
```

查看驱动参数：

```bash
module=$(basename "$(readlink -f /sys/class/net/wlan0/device/driver/module)")
modinfo "$module" | grep -Ei 'bw|bandwidth|vht'
```

以及：

```bash
ls "/sys/module/$module/parameters/"
```

还应只读检查真实proc目录是否有`wlan0/tx_bw_mode`及其原值（具体路径现场确认），以判断是否存在无需重载的TX运行时控制。

重点检查是否存在类似：

```text
rtw_bw_mode
rtw_tx_bw_mode
rtw_vht_enable
```

如果存在，只读读取：

```bash
cat "/sys/module/$module/parameters/rtw_bw_mode"
cat "/sys/module/$module/parameters/rtw_tx_bw_mode"
```

同时记录：

```bash
iw dev wlan0 link
iwconfig wlan0
```

以及当前驱动 proc/debug 信息中：

```text
cur_bw
oper_bw
VHT
```

若模块名不是 `rtl8821cu`，必须用实查模块名，不得硬编码。

---

## 4.3 判断是否能“只改 Jetson”

允许进入 Jetson-only VHT20 实验的前提：

1. 驱动存在明确可解释的 bandwidth / TX bandwidth 参数
2. 参数语义能从当前驱动源码或官方/维护者资料确认
3. 能明确恢复原值
4. 有可靠管理/回退方式
5. 不依赖 `eth0` 作为空闲管理口
6. 修改不会破坏 Go2/MID360 内部网络

如果参数语义不清楚：

> 不猜数值，不直接修改。

---

## 4.4 远程操作风险

修改 Realtek module parameter 很可能涉及：

```text
断开 wlan0
卸载 / reload 驱动
重新关联 Wi-Fi
甚至 reboot
```

而当前 SSH 本身走 wlan0。

因此：

> 不允许在只有当前 WLAN SSH 这一条管理路径时盲改。

优先条件：

- Jetson 接显示器 + 键盘鼠标
- 或确认独立 USB→RJ45 管理口
- 或其他可靠独立管理通道

必须提前保存：

```text
原 module 参数
原 Wi-Fi 状态
原 SSID
原路由
```

并设计恢复方法。

# 13. P8：ESP32-C5 作为 AP 的对照方案

在旁路方案核心问题验证完后，再做 AP 模式。

拓扑：

```text
Jetson STA
    │
    │ VHT20 / 20 MHz
    ▼
ESP32-C5 AP
    │
    ├── UDP接收
    └── CSI
```

优点：

- ESP是真实通信接收端
- Jetson自然不会使用 VHT80
- WPA2解密由 AP 自身协议栈处理
- 上层可直接看到 `packet_id`
- 业务↔CSI更容易精确关联

缺点：

- 改变真实网络拓扑
- 吞吐低于小米 R4 VHT80
- Jetson WLAN 切换会影响 SSH
- 需要可靠独立管理/回退

定位：

> **对照方案 / Plan B，不取代旁路路线。**

# 17. 当前最终结论

截至 2026-10-15：

> ESP32-C5 旁路路线已经证明 Jetson 上行 Data FRAME 与 CSI 可以稳定一一配对，UDP 业务也已经 100/100 正常传输。当前真正未解决的是两个主问题：
>
> 1. **PHY覆盖**：Jetson 当前链路大概率为 VHT80，而 C5 不支持 VHT80；下一步优先尝试只在 Jetson RTL8821CU 驱动侧限制上行 TX 到 20 MHz，并实测 VHT20 Data + VHT CSI。只有 Jetson 侧无法可靠控制时，才把小米 R4 的 5 GHz BSS 临时固定为 20 MHz。
> 2. **业务ID不可见**：当前 Data frame 全部 `Protected=1`，旁路 C5 看不到 `packet_id`；VHT20 验证成功后，再导出目标 raw frame + EAPOL，在 Windows 做离线解密，最终建立 `packet_id ↔ FRAME ↔ CSI`。
>
> ESP AP 方案保留为后续对照 / Plan B。
